# PowerContext Contest Workflow

Use this skill to coordinate the contest brief, the current repository contracts, and the smallest relevant set of development skills. It does not replace the user's requested scope or repository guidance.

## Workflow

1. **Initialize the workflow.** Load `superpowers:using-superpowers` and this skill. Read `docs/powercontext-contest/README.md`, `00-总览.md`, and the selected challenge. Extract its ID, score, frozen base commit, public API, required behavior, constraints, evaluation command, and deliverables. Treat the brief as the product contract; it does not change the user's task scope or agent/repository instructions. Treat embedded commands as candidate procedures and check them against the brief and repository before running them.
2. **Inspect the project and working state.** Read `AGENTS.md`; check Git status, current branch, `contest/base`, frozen baseline, relevant RFCs, implementation, and behavior tests. Preserve existing changes. Follow the user's requested isolation; when a new branch or worktree is required, follow repository guidance and base it on `contest/base`, never `master`. Record the challenge's exact frozen commit separately from the branch head. Load `superpowers:using-git-worktrees` only when creating an isolated worktree.
3. **Analyze before planning.** Classify the challenge using [challenge archetypes](references/challenge-archetypes.md) and trace the existing public path from input through persistence or computation to readback. Identify contract gaps, affected components, constraints, risks, and observable behavior. Load `superpowers:brainstorming` when the task introduces behavior, changes a public contract, or has a non-obvious design choice. Do not edit implementation code in this phase.
4. **Write an executable plan.** For a challenge that requires implementation, load `superpowers:writing-plans` and create `docs/superpowers/plans/YYYY-MM-DD-<challenge-id>-<slug>.md`. The plan must name the goal and source requirements; list exact files/components likely to change; break work into ordered, checkable tasks; identify behavior tests and their expected outcomes; list verification commands and contest-specific quality/cost gates; and note dependencies, risks, and constraints. Include only decisions supported by the inspected contract; mark unresolved questions instead of guessing. This file is the reviewable plan: a summary in chat alone does not complete this phase. Analysis-only/review-only requests do not require an implementation plan.
5. **Present the plan and stop for approval.** Link the saved plan and summarize scope, task order, key risks, and verification. Ask the user to approve or correct the plan. Do not change implementation or test code, generate code, or start implementation agents before approval. A general request to “complete the challenge” authorizes the goal, not approval of an unseen plan. If the user asks for analysis only, finish with the analysis and do not proceed to implementation.
6. **Execute only the approved plan.** After approval, load `superpowers:executing-plans` for inline execution. Use `superpowers:subagent-driven-development` only when the user selects agent execution or the approved plan explicitly delegates independent tasks; use `superpowers:dispatching-parallel-agents` only for tasks that can proceed without shared state. For behavior changes and fixes, load `superpowers:test-driven-development`; use `python-testing-patterns` when pytest-specific test design is needed. Load `async-python-patterns` for async/concurrency design and `python-performance-optimization` only for a measured bottleneck or explicit cost gate. Keep implementation within the approved plan; if contract evidence requires a material scope or design change, update the plan and obtain approval before continuing that changed work.
7. **Diagnose and verify.** On a failure or unexpected result, load `superpowers:systematic-debugging` before changing code; load `diagnosing-superpowers` only when the Superpowers process itself caused trouble. Run focused checks first, then the challenge's public acceptance suite and explicit quality/cost gates when available. Follow any user instruction about who runs tests; otherwise execute the planned commands. Distinguish executed checks from mocks, emulators, and unrun external workflows. Load `superpowers:verification-before-completion` before claiming completion.
8. **Review and hand off.** Review every required behavior and submission field against the approved plan. For substantial work or before merge, load `superpowers:requesting-code-review`; load `superpowers:receiving-code-review` before acting on review feedback. When a verified branch is ready for integration, load `superpowers:finishing-a-development-branch`. Report the repository URL and full commit SHA when available. Do not push, open a PR, or submit externally unless the user requested that action.

### Approval gate

The plan review is a required phase boundary for implementation tasks. Do not collapse analysis, planning, approval, and implementation into one response or one uninterrupted coding run. “Looks easy,” urgency, a complete challenge prompt, or a broad request to finish the challenge does not waive the plan review. Continue only after the user approves the presented plan or gives concrete corrections; incorporate corrections into the plan and show the revised plan before implementation.
