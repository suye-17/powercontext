# 高德周边地点推荐

根据用户给出的城市、起点和自然语言需求，使用高德 MCP 的**周边搜索**与**步行路径规划**，返回最多 3 个真实、可步行到达的地点。每个地点都是从同一起点出发的独立备选，不要串成多站行程。

## 适用场景

- 用户给出或平台提供起点坐标，想找附近的咖啡馆、餐厅、公园等地点。
- 用户提出步行时间上限、推荐数量、排序偏好（如“优先近一点”）。
- 用户要求给出每个地点的地址、步行距离、步行时间和推荐理由。

不适用：驾车、公交、骑行路线规划；跨城市行程；多站路线编排；实时排队、安静程度、评分等工具未提供的信息。

## 一、解析需求

提取以下字段；缺失时按默认值处理，不要编造：

| 字段 | 说明 | 缺失/默认 |
|---|---|---|
| 城市 | 用户给出的城市 | 只用于关键词搜索或地理编码；不要凭坐标猜城市 |
| 起点 | 坐标或地点名称 | 平台或用户会提供坐标；高德坐标顺序为“经度,纬度” |
| 地点类型/关键词 | 咖啡馆、餐厅、公园、品牌名等 | 必填；单轮任务中按最可能的类别搜索并写明假设；只有在可追问时才问用户 |
| 步行时间上限 T | “步行不超过 15 分钟” | 无上限时不做时间过滤，但仍需查询步行路线 |
| 推荐数量 N | “最多 3 家”“推荐 2 个” | 默认 3；最终不超过 3 |
| 排序偏好 | “优先近一点”等 | 默认按实际步行时间从短到长 |
| 其他条件 | 安静、不排队、营业中、评分高等 | 只有工具返回对应数据时才作为条件，否则标注“未核实” |

- “15 分钟左右”按 15 分钟处理；“半小时”按 30 分钟处理。
- 解析后用一句话复述关键条件，例如：“从<起点>出发，找<类型>，步行 ≤15 分钟，最多 3 个，优先近的。”

**起点处理：**

1. 平台或用户给出坐标时，直接使用该坐标，不要重新地理编码或偏移。
2. 只给出地址/地标时，调用 `maps_geo`（参数 `address`、`city` 可选）取坐标；仍无法确定时说明坐标无法核实并请用户提供坐标，不要猜。
3. 坐标统一为高德 `经度,纬度`；如果输入明确是 `纬度,经度`，先交换再调用。

## 二、选择工具

优先使用下表中的工具；以平台实际暴露的工具 schema 为准。若工具名不同，选择名称/描述对应“周边搜索”“地点详情”“步行路径规划”“地理编码”的工具。

| 能力 | 首选工具 | 关键参数 | 用途 |
|---|---|---|---|
| 周边搜索 | `maps_around_search` | `location`（经度,纬度）、`keywords`、`radius`（米） | 找起点周边的候选地点 |
| 地点详情 | `maps_search_detail` | `id` | 在周边结果缺少地址/坐标时补齐 |
| 步行路线 | `maps_direction_walking_by_coordinates` | `origin`、`destination`（均为经度,纬度） | 获取真实步行距离与时间 |
| 步行路线（地址版） | `maps_direction_walking_by_address` | `origin_address`、`destination_address`、`origin_city`（可选）、`destination_city`（可选） | 坐标工具不可用时的备选 |
| 地理编码 | `maps_geo` | `address`、`city`（可选） | 起点只有地址时取坐标 |
| 关键词搜索（备选） | `maps_text_search` | `keywords`、`city`（可选）、`citylimit`（可选） | 周边搜索不可用时找候选；必须再逐一路线查询 |

**禁止替代：**

- 不要用 `maps_direction_driving_*`、`maps_direction_transit_integrated_*`、`maps_bicycling_*` 的时长冒充步行时间。
- 不要用 `maps_distance` 或周边搜索返回的 `distance` 字段代替步行路线距离；即使 `maps_distance` 返回步行测量，也不等同于步行路径规划，只能用于候选预排序。
- 不要用直线距离、地图估算或模型常识补算步行时间。

## 三、查询与筛选流程

### 1. 周边搜索

调用 `maps_around_search`：

- `location`：起点坐标，格式 `"经度,纬度"`。
- `keywords`：用户的核心类别词。例如“咖啡馆”用“咖啡”，“餐厅”用“餐厅”或“美食”，“公园”用“公园”；品牌名直接用品牌名。
- `radius`：
  - 有步行上限 T 时：`radius = min(max(T × 100, 500), 5000)` 米。例：15 分钟 → 1500 米；10 分钟 → 1000 米；5 分钟 → 500 米。
  - 无步行上限时：默认 1500 米。
  - `radius` 只是搜索包络，**最终是否推荐只看步行路线时长**。

结果为空或清洗后候选少于 5 个时，可把 `radius` 扩大到原来的 1.5 倍再搜一次（最多 5000 米）。扩大后仍为空或候选仍不足，按实际结果处理；最多扩大一次，不要无限扩大。

### 2. 候选清洗

从返回的 `pois` 中：

1. 按 `id` 去重；没有 `id` 时按“名称 + location”去重。
2. 没有可用 `location` 但有 `id` 的候选，先用 `maps_search_detail` 补齐坐标；仍缺 `location` 才丢弃（无法规划路线）。
3. 检查 `type` 与名称是否匹配用户要的类型。只有 `type` 明确包含用户类别，或名称明确匹配时才保留；明显不符的（例如要“咖啡厅”却返回“咖啡器具/咖啡豆零售”）丢弃。边界候选不得用于凑数；若保留，推荐理由必须如实写出实际类型。
4. 用户给了多个类别时，分别搜索后合并候选，按后续步行时间统一排序；类别控制在 2–3 个以内。超过 3 个类别时，先按最重要的 2–3 个搜索，并在回答中说明未覆盖的类别。
5. 用户明确要某个品牌时，只保留名称/类型确实匹配该品牌的结果；没有就如实说没有，不要用其他品牌替代。

### 3. 预排序与路线查询

1. 用周边搜索返回的 `distance`（直线距离，若有）或由坐标计算的直线距离，对候选从近到远排序；所有距离/时长字段先转成数值再比较。该距离只用于决定先查哪些路线，**不写进最终答案**。
2. 对清洗后的候选按直线距离从近到远分批调用步行路线：先查最近 **6** 个；如果合格数量不足目标数量且还有未查询候选，再按距离顺序补查。最多核查 **20** 个候选；若清洗后候选超过 20 个，只核查最近的 20 个，并在回答中说明“已核查最近 20 个候选”。不要在未核查全部候选时声称“全局最短”或“只有这些地点”。
3. 每次路线查询：
   - `origin` = 起点坐标；`destination` = 候选的 `location`。
   - 从返回 JSON 读取第一条步行方案的 `distance`（米）和 `duration`（秒）。常见结构为 `route.paths[0]` 或 `paths[0]`；若只有 `steps`，累加各步骤的 `distance` 和 `duration`；字符串数值先转成数字。
   - 若返回多条方案，使用第一条推荐方案；不要自行混合多条方案的数据。
4. 资格判断：
   - 有步行上限 T 时：`duration_seconds <= T × 60` 才合格；**严格按原始秒数比较**，不要先四舍五入再比较。
   - 无步行上限时：路线查询成功即合格。
   - 路线查询失败、缺少 `distance` 或 `duration`、或返回的起终点明显与请求不符：该候选不合格，不得用估算值或周边直线距离补上。
5. 某个候选路线查询失败时，可原样重试一次；重试计入总调用预算。仍失败则跳过，并在最终说明中写“有候选因路线查询失败未纳入”，不要编造。

### 4. 排序与选取

1. 合格候选按**实际步行时长（秒）从短到长**排序；时长相同按实际步行距离从短到长；再相同按名称稳定排序。
2. 用户说“优先近一点”时，默认按实际步行时间从短到长（到达更快）；回答开头写“按实际步行时间（到达更快）排序”，并补一句“如果你更在意路程更短，可以改按步行距离排序”。用户明确说“优先距离最短/少走路”时，改为按实际步行距离从短到长、距离相同再按时间。用户有其他偏好时，只有工具数据支持该偏好才调整排序，否则说明“该偏好缺少数据，按步行时间排序”。
3. 推荐理由必须与排序指标一致：第 1 名写“最短”，第 2/3 名写“较短”；按时间排序写“步行时间最短/较短”，按距离排序写“步行距离最短/较短”。不要在没有核查全部候选时声称全局最短。
4. 取前 `min(N, 3)` 个。用户要求超过 3 个时，最多给 3 个，并说明“按上限最多推荐 3 个”；即使合格候选超过 3 个，也只给前 3 个。
5. 不足数量时给多少算多少，并说明原因；不要为凑数放宽硬条件。

## 四、回答格式

优先用表格；渲染受限时用编号列表，字段保持一致。实际回答时把 `<...>` 替换为工具返回值。

以下模板中的“步行 ≤ <T> 分钟”只在用户给出步行上限时保留；无上限时删除该子句，排序写“按步行时间”。

**有结果（K > 0，包括 K < N 的结果不足情况）：**

```text
从<起点>出发，按<实际排序指标>从近到远，为你找到 <K> 个符合条件的地点（<类型>，步行 ≤ <T> 分钟）：

| 排名 | 地点 | 地址 | 步行距离 | 步行时间 | 推荐理由 |
|---|---|---|---|---|---|
| 1 | <高德返回的名称> | <高德返回的地址> | <路线 distance> 米 | 约 <duration 换算> 分钟 | <一句基于路线/类型的事实理由> |
| 2 | … | … | … | … | … |

说明：步行距离与时间为高德步行路线规划结果；<未核实信息说明>。
```

要求：

- 只要 K > 0，就必须用上面的表格列出每个已确认地点的名称、地址、步行距离、步行时间和理由；结果不足时不能只写一句计数。
- 地点名称、地址必须来自高德返回结果；距离、时间必须来自步行路线返回结果。
- 结果不足时，在表格后补一句：“你要求 <N> 个，按上限最多 3 个；在已核查的候选中实际找到 <K> 个符合条件的地点。”再给出放宽建议。如果因 20 个上限没有核查完，写“在已核查的最近 20 个候选中”。
- 无步行上限时省略“步行 ≤ <T> 分钟”；开头按实际排序指标写“按步行时间从近到远（到达更快）”或“按步行距离从近到远”。
- 时间由 `duration` 秒换算为分钟，可保留一位小数；不要声称比工具返回值更精确。
- 推荐理由只写有数据依据的内容，例如“在已核查的候选中步行时间最短（约 8 分钟）”“类型为咖啡厅，步行约 11 分钟，满足 15 分钟上限”。第 1 名写“最短”，第 2/3 名写“较短”。
- 不要写“环境安静”“不用排队”“评分很高”等未核实信息；用户问到这些时，明确写“未核实”。
- “未核实信息说明”按实际字段写：工具返回营业时间（如 `open_time`）时写“营业时间：…；当前是否营业未核实”；没有营业字段时写“营业状态未核实”；排队、安静、评分同理，只有工具明确返回对应字段才引用。
- 每个地点都是同一起点的独立备选，不要写成“先去 A 再去 B”的多站行程。

**无结果（K = 0）：**

```text
在起点周边 <radius> 米范围内，未找到符合“<类型>”且步行 ≤ <T> 分钟的地点，因此本次不推荐。
可以尝试放宽步行时间、换一个地点类型，或提供更具体的起点。
```

如果因 20 个上限没有核查完，改为“在已核查的最近 20 个候选中，未找到……”。

**工具异常（仅当周边搜索本身失败或全部路线都失败）：**

```text
本次高德地点/路线查询失败（<简短错误>），无法核实地点和步行时间，因此不给出推荐。请稍后重试或放宽条件。
```

不要把超时地点放进推荐表；如确需提及，只能放在“不符合条件（不推荐）”的说明中，并明确写出其步行时间超过上限。部分路线失败时，仍按上面的表格推荐已确认候选，并在说明中写“有候选因路线查询失败未纳入”，不要套用全局工具异常模板。

## 五、异常与边界处理

| 情况 | 处理 |
|---|---|
| 周边搜索失败 | 原样重试一次；仍失败可尝试 `maps_text_search` + 逐一路线查询（必要时用 `maps_search_detail` 补齐坐标，只保留能路线查询的候选）；再失败则如实说明服务异常 |
| 路线查询失败 | 重试一次（计入总调用预算）；仍失败则跳过该候选并说明，不得用直线距离估算 |
| 路线工具不可用/无任何路线数据 | 不得按直线距离估算步行时间或推荐；只说明无法核实，建议重试或放宽条件 |
| 只能确认部分候选 | 只推荐已确认的候选；未确认的候选放在“未核实”说明中，明确不能作为符合条件的推荐 |
| 周边搜索成功但部分路线失败 | 推荐已确认候选，说明“有候选因路线查询失败未纳入”；不要套用全局工具异常模板 |
| 用户要求放宽条件后纳入某候选 | 只有该候选的路线时间确实 ≤ 放宽后的上限才能纳入；不得用直线距离推断 |
| 周边搜索无结果 | 扩大半径 1.5 倍再试一次；仍无结果则如实说明，不编造地点 |
| 有候选但都超时 | 不推荐超时地点；说明“找到候选但步行均超过 T 分钟”，建议放宽条件 |
| 结果少于 N | K>0 时仍按表格列出每个地点；给实际合格数量并说明原因，不用超时/类型不符的地点凑数 |
| 地址缺失 | 用 `maps_search_detail` 按 `id` 补齐；仍缺失则标注“地址未返回”，不要编造 |
| 缺少步行距离 | 该候选不纳入推荐；不得用周边 `distance`/直线距离补；说明路线数据不完整 |
| 缺少步行时长 | 该候选不纳入推荐；说明路线数据不完整 |
| 用户问营业/排队/安静/评分 | 只有工具明确返回当前营业状态字段（如 `open_status`）才可写“营业中/已打烊”；只有 `open_time` 时只能引用“营业时间：…；当前是否营业未核实”；其他字段同理，没有就写“未核实” |
| 用户要求超过 3 个 | 最多推荐 3 个并说明上限 |
| 用户给多个类别 | 分别搜索、合并、按步行时间统一排序；类别不超过 2–3 个，超出时说明 |
| 清洗后候选超过 20 个 | 只核查最近 20 个，回答中说明“已核查最近 20 个候选”；不要声称全局最短或无其他结果 |

## 六、禁止事项

- 不得编造地点名称、地址、坐标、距离、步行时间、评分、营业时间、排队或安静程度。
- 不得用直线距离、驾车/公交/骑行时间、地图估算替代步行路线结果。
- 不得用“连锁品牌通常安静/环境稳定/不用排队”等品牌印象或常识替代工具字段。
- 不得在路线查询失败或路线工具不可用时用直线距离估算步行时间，或把未核实候选列为推荐。
- 不得用直线距离推断某候选“很可能符合”时间上限；放宽条件后也要以实际路线秒数为准。
- 不得用周边搜索的 `distance`/直线距离补缺失的步行距离。
- 不得把 `open_time`（营业时间）说成“营业中”；只有当前营业状态字段才可写营业中。
- 不得在未核查全部候选时声称“全局最短”或“只有这些地点”。
- 不得把步行超时的地点列为“符合条件”的推荐。
- 不得为了凑够数量放宽类型或时间条件。
- 不得把多个推荐写成多站行程。
- 不得在 Skill 或回答中填写、索要高德 API Key；运行环境和密钥由评测平台配置。
- 不得输出与工具返回不一致的“精确”数字；换算和四舍五入要说明是“约”。

## 七、提交前自检

回答前逐项检查：

- [ ] 每个地点名称、地址都来自高德返回结果。
- [ ] 每个距离、时间都来自步行路线返回结果，不是直线距离或其他交通方式。
- [ ] 所有推荐都满足类型要求和步行时间上限（按原始秒数比较）。
- [ ] 推荐数量 ≤ min(用户要求, 3)；即使合格候选更多，也只给前 3 个。
- [ ] K>0 时，即使结果不足，也用表格列出每个地点的名称、地址、距离、时间和理由。
- [ ] 排序与步行时长/距离一致，并符合用户“优先近一点”等偏好；没有在未核查全部候选时声称全局最短。
